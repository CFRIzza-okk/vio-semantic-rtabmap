============================================================

将现有 ROS 2 Humble + D435 + RTAB-Map 语义建图项目，接入 TX1 上的 ROS 1 Melodic Wheeltec R680 麦轮底盘，最终形成：

  TX1 ROS 1 底盘与里程计

  RTAB-Map 地图
      ↓

      ↓

      ↓
  ROS 2 安全仲裁
      ↓
  /cmd_vel_safe
      ↓
  ROS 1/ROS 2 relay
      ↓
  TX1 /cmd_vel

十三、网络问题根因（已定位，重要）
============================================================

调查结论：TX1 与 ROS 2 主机其实在【同一根网线】上，但两端
IP 子网不匹配，所以互相不通。这不是 TX1 掉线。

证据：

1) TX1 的 eth0：

   link/ether 00:04:4b:9c:4b:d2
   inet 192.168.1.102/24
   state UP（LOWER_UP，网线已连接）

   TX1 的 wlan0：

   state DORMANT, NO-CARRIER（WiFi 未连接）

2) TX1 的路由表只有：

   192.168.1.0/24 dev eth0
   169.254.0.0/16 dev eth0

   没有默认路由，因此 TX1 只能在 192.168.1.0/24 内通信。

3) ROS 2 主机（Jetson）邻居表关键条目：

   192.168.1.102 dev eno1 lladdr 00:04:4b:9c:4b:d2 STALE
   192.168.1.102 dev wlP1p1s0  FAILED

   00:04:4b:9c:4b:d2 正是 TX1 eth0 的 MAC，而 Jetson 是在
   【eno1 有线口】上学到这个 MAC 的。

   => 说明 TX1 的 eth0 与 Jetson 的 eno1 处于同一根网线/L2 段。

4) Jetson 的网口地址：

   wlP1p1s0（WiFi，SSID=XTKZ）: 192.168.1.16/24  ← 默认路由走这里
   eno1（有线）:               192.168.2.15/24

5) 结果：

   TX1 eth0    = 192.168.1.102/24
   Jetson eno1 = 192.168.2.15/24

   同一根线，不同子网 => ARP 无法互答 => 双向不通。
   Jetson 发往 192.168.1.102 的包按路由走 WiFi 出口，
   TX1 的网线根本收不到，所以 WiFi 网段扫描也找不到 .102。

结论与修复方案：

  推荐方案：让有线链路两端一致到 192.168.2.0/24。
  （TX1 之前曾出现 192.168.2.102，说明这就是原本的配置。）

  TX1 本地执行：

    sudo ip addr add 192.168.2.102/24 dev eth0
    ping -c 3 192.168.2.15

  能 ping 通即确认链路正确，然后写进 NetworkManager 使其持久化：

    nmcli connection show
    nmcli connection modify <连接名> +ipv4.addresses 192.168.2.102/24
    nmcli connection up <连接名>

  TX1 的 ROS 环境相应改为：

    export ROS_MASTER_URI=http://192.168.2.102:11311
    export ROS_IP=192.168.2.102
    unset ROS_HOSTNAME

  ROS 2 主机侧：NoMachine 继续走 WiFi 192.168.1.16，
  ROS 通信走有线 192.168.2.15，两者互不影响。

  不推荐：把 Jetson eno1 改成 192.168.1.x 去迁就 TX1。
  那样会让 eno1 和 wlP1p1s0 处于同一子网，产生 ARP/路由歧义。

  注意：relay 配置里的 peer_host 目前是 192.168.1.102，
  链路切到 192.168.2.0/24 后必须改成 192.168.2.102。

十五、已完成：TX1 时间同步（自定义轻量方案）
============================================================

问题：

  TX1 的 RTC 不可用。

    RTC time: 2000-01-05
    hwclock -w 返回成功但回读仍是 2000-01-05（实际未写入）

  TX1 也没有外网：

    ping 223.5.5.5 失败

  systemd-timesyncd 虽然 active，但 System clock synchronized: no。

  结果：每次重启后 TX1 时钟回到 2023-08-27。
  实测偏差 98,724,855 秒 = 1142.65 天 ≈ 3.13 年。

影响：

  relay 会保留 ROS 消息头时间戳。3 年偏差会导致 ROS 2 侧
  tf2 / RTAB-Map 时间戳过旧、外推失败。

选定方案（用户选择 A：轻量自定义同步服务）：

  Jetson 侧（时间源）：

    tools/time_sync_server.py
    监听 UDP 高位端口 10123（避免端口 123 需要 root）
    协议：MAGIC=b"R680TS01"
      请求  MAGIC | seq:u64
      响应  MAGIC | seq:u64 | t1:u64 | t2:u64
      （大端，纳秒）

    Jetson 上用用户级 systemd 服务开机自启：
      ~/.config/systemd/user/r680-time-sync-server.service
      Linger=yes（已确认），因此无需登录即随开机启动
      模板文件：tools/r680-time-sync-server.user.service

  TX1 侧（时间客户端）：

    /home/wheeltec/time_sync_client.py
    用 ctypes 调用 clock_settime(CLOCK_REALTIME)，因此需要 root
    偏移算法：offset = ((t1 - t0) + (t2 - t3)) / 2
    取 RTT 最小的样本，降低网络抖动影响
    兼容 Python 2.7 / 3.6（TX1 是 Python 3.6.9，
    不能用 time.monotonic_ns()，该 API 需 Python 3.7+）

    TX1 上用系统级 systemd 服务（以 root 运行）：
      /etc/systemd/system/r680-time-sync.service
      ExecStart=/usr/bin/python3 /home/wheeltec/time_sync_client.py
                --server 192.168.2.15 --port 10123
                --interval 10 --threshold 0.005 --timeout 1.0 --samples 3
      Restart=always
      模板文件：tools/r680-time-sync.service

实测结果：

  - 协议精度：RTT 约 0.46–0.60 ms
  - 首次修正：一次性步进 +98,724,804 秒（+1142.65 天）
  - 稳态精度：TX1 与 Jetson 偏差保持 1–5 ms
  - TX1 时钟漂移率：约 0.129 ms/s（约 129 ppm）
    因此 --threshold 0.005 + --interval 10 约每 40 秒
    进行一次约 5 ms 的小幅步进
  - 自愈验证：人为把 TX1 时钟设回 2023-08-27，服务在
    10 秒内自动修正 1142.64 天，无需任何人工干预
  - 两个服务均 enabled + active，且已链接进开机 target：
      Jetson: default.target.wants/r680-time-sync-server.service
      TX1:    multi-user.target.wants/r680-time-sync.service

  自愈测试已经完整复现"时钟错误 + 服务运行"的重启后场景，
  因此没有为验证时间同步而额外重启 TX1。
